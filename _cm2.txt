fix(hook): 修两个让 hook 大面积失效/崩溃的自伤 bug —— 真机日志逐条坐实

第 10 次真机日志（构建 90e2611）是第一次 hook 真正装上的运行，也是一次性
暴露两个 bug 的运行。日志本身写得很清楚：

  [install] 阶段 2/3 完成 —— 安装阶段全部走完，未崩溃
  [boot] 探针安装完毕，等待播放器触发…
  12:06:12.745 [request] NSURLRequest requestWithURL host=i2.hdslb.com
  12:06:12.746 [session] 媒体请求 method=GET host=i2.hdslb.com
  （日志到此为止，进程死亡）

bug 1：转发方式挂在系统 class cluster 上 -> 第一次 task resume 就崩
  NSURLSessionTask 是系统 class cluster，实例真类是 __NSCFURLSessionTask
  （CoreFoundation 支撑）。这类具体类可能自带 forwardInvocation: /
  methodSignatureForSelector:，把我们的转发器遮住，转发链拿不到签名 ->
  消息无人认领 -> 抛异常闪退。
  转发那套在普通 NSObject 子类上很成熟（Aspects 就用它），系统类上不安全。
  修法：新增「直连 hook」原语 hookClass:selector:expectShapes:directImp:storeOld:
  —— 先按真机 encoding 校验形状，对上了再直接把实现换成调用方写的 C 函数。
  resume 的签名是 v16@0:8（零参数），void f(id, SEL) 与之严格对应，
  不存在读错寄存器的可能，且完全绕开 _objc_msgForward 与转发链。
  同时不再挂 NSURLSession 的 dataTaskWithURL: 系列：resume 已全覆盖，
  多挂系统类的工厂方法只是徒增风险。

bug 2：自己的 forwardInvocation: 被误判成「类自带」-> 每个类只能装上第一个 hook
  装上第一个转发 hook 时，我们**自己**会给这个类加一个 forwardInvocation:。
  第二个 hook 走到「类自带 forwardInvocation: 就拒绝」的检查时，
  class_copyMethodList 查到的是我们自己加的那个，于是被拒。
  真机日志里就是：play ✓ 然后 prepareToPlay / initWithContentURL: 全 ✗，
  22 个 URL hook 只装上 4 个；IJKMediaPlayerItem 上最关键的 willOpenUrl: /
  setUrl: 一个都没装上。
  修法：查到 forwardInvocation: 时先看实现是不是我们自己的 bsp_forward，
  是则视为「转发器已就绪」并复用，不再重复添加。

新增 hook 机制自检（用两次事故换来的，务必保留）
  在装真实 hook 之前，先在一个临时类上把整条链路跑通：
    ① 同一个类连挂两个 hook，必须都成功（覆盖 bug 2）
    ② 真的给这个类发一次消息，必须能正常走到原实现（覆盖转发链路本身）
  任一项失败就大声喊出来，并提示「不要继续测播放」。这两个 bug 的共同点
  就是安装逻辑坏了而日志只显示「没装上」，自检把这类问题挪到启动瞬间暴露。

新增 hook 分组开关
  {Documents}/biliprobe/hooks.txt，每行「组名=on|off」：
    player（播放器生命周期/正证据）  缺省 on
    url   （URL 改写）               缺省 on
    net   （系统网络类）             缺省 off —— 刚出过事的那个，要看再打开
  真机闪退时唯一能做的就是二分，有了这个文件用户自己就能定位，不用等我出包。

另修：改写返回值时的野指针
  NSInvocation 不 retain 返回值，而 ARC 会在 after 块作用域结束时释放局部强引用
  —— 调用方拿到的是野指针。加了有上限的强引用池兜住。
