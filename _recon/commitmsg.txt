feat(probe): 改找「缓存写法」而非「下载者」—— 挂零参/单参的缓存路径 provider

前七次真机都在找"谁在下载视频字节"，结果全部网络层观测点为 0
（AVAssetResourceLoader / NSURLSession / NSURLRequest / NSURLProtocol /
NSURLConnection / AVURLAsset / BBRMediaDownloader / 预加载 全空）。

而**缓存盘点证明字节确实落到本地**（上一次真机，构建 a9e542f）：
  /…/Library/Application Support   594,860,978 字节 / 13,171 个文件  ← 595MB
  /…/Library/Caches                 34,938,465 字节 / 537 个文件
  /…/tmp/dash_cache                  3,869,073 字节 / 10 个文件
  /…/tmp/ijkvideo                            0 字节 / 0 个文件
  /…/tmp/p2p_cache                           0 字节 / 0 个文件   ← P2P 未启用
  /…/Library/Caches/p2p_cache                0 字节 / 0 个文件   ← 同上

因此换切入点：不问"谁下载"，而问"缓存文件写在哪、谁提供这个路径"。

为什么这批 hook 不会像上次那样崩（关键论证）：
  上一次闪退的两个原因都源于**签名不确定**：
    ① performSelector 取整数返回值当对象 → objc_retain 读 0xffffffff
    ② 多参数方法（IJKDashStreamItem.initWithStreamId:…）按推测签名读寄存器，
       参数若是对象则被垃圾指针 retain
  而本次挂的三个方法**只涉及对象参数，参数个数固定（0 或 1）**：
    IJKP2PServerResolver                + getAndCreateP2pConfigPath   @@:
    BBPlayerInteractiveResourcePreload  + savedFolder                 @@:
    BBPlayerInteractiveResourcePreload  - downloadWithUrl:savedPath:relativePath:  v@:@@@
  结构上不存在"把整数当对象"的可能，因此即使理解有偏差也不会崩。

其中 downloadWithUrl:savedPath:relativePath: 是最有价值的落点：
它同时给出 **CDN URL 与落盘路径**，是"下载 + 落盘"的合流点，
也正是阶段 2「改 host / 多 CDN 池」需要插进去的地方。

新增观测点输出（[path] 标签）：
  ★★ downloadWithUrl ← host / url / savedPath / relativePath
  ★  savedFolder → 缓存根目录
     getAndCreateP2pConfigPath → p2p 配置路径

[verdict] 新增最高优先级分支：
  ★★★ 找到了！downloadWithUrl 命中 N 次 → 阶段 2/3 落点就是它
心跳行同步输出「落盘=N」。
